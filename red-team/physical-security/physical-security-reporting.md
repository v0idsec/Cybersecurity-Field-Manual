# Physical Security Reporting

A reference for documenting physical security assessment results in a clear, evidence-based and actionable format.

A professional report should explain what was assessed, what was observed, why it matters and how the organisation can improve its security posture.

## Reporting objectives

- Communicate risk to technical and non-technical stakeholders.
- Document confirmed weaknesses.
- Explain business and operational impact.
- Provide practical remediation guidance.
- Preserve relevant evidence.
- Support remediation and retesting.

## 1. Report structure

A physical security assessment report should include:

1. Document control.
2. Executive summary.
3. Assessment objectives.
4. Scope and exclusions.
5. Methodology.
6. Assessment limitations.
7. Overall observations.
8. Detailed findings.
9. Risk summary.
10. Remediation roadmap.
11. Retest results.
12. Appendices and evidence register.

## 2. Executive summary

The executive summary should explain:

- Why the assessment was conducted.
- Which facilities were assessed.
- The overall security posture.
- The most significant risks.
- Potential business consequences.
- Priority remediation actions.

Avoid excessive technical detail.

## 3. Scope documentation

Document:

- Organisation.
- Facility names or identifiers.
- Approved buildings and areas.
- Assessment dates.
- Assessment personnel.
- Systems reviewed.
- Testing activities.
- Exclusions.
- Limitations.

Avoid publishing sensitive facility details unnecessarily.

## 4. Finding structure

Each finding should contain:

| Field | Description |
|---|---|
| Finding ID | Unique reference |
| Title | Concise description |
| Severity | Risk rating |
| Location | Affected facility or area |
| Category | Relevant security control |
| Description | What was observed |
| Expected state | Intended security behaviour |
| Observed state | Actual behaviour |
| Evidence | Supporting material |
| Impact | Potential consequence |
| Likelihood | Probability of occurrence |
| Recommendation | Proposed remediation |
| Retest criteria | How remediation can be verified |

## 5. Finding categories

Suggested categories:

- Perimeter security.
- Site access.
- Visitor management.
- Credential management.
- Access-control systems.
- Locking systems.
- CCTV and surveillance.
- Intrusion detection.
- Alarm management.
- Server room security.
- Environmental protection.
- Critical infrastructure.
- Third-party access.
- Security procedures.
- Incident response.

## 6. Severity assessment

Use the organisation's approved risk methodology where one exists.

A practical qualitative model:

| Severity | Description |
|---|---|
| Critical | Severe exposure with potential for major business or safety consequences |
| High | Significant weakness affecting important assets or restricted facilities |
| Medium | Meaningful weakness requiring planned remediation |
| Low | Limited exposure or procedural deficiency |
| Informational | Observation or improvement opportunity without a confirmed vulnerability |

Consider:

- Likelihood.
- Impact.
- Asset sensitivity.
- Existing controls.
- Ease of detection.
- Operational dependencies.
- Safety implications.

Do not assign severity based only on how easy a weakness appears to exploit.

## 7. Evidence requirements

Evidence should be:

- Relevant.
- Accurate.
- Sufficient.
- Traceable.
- Securely stored.
- Proportionate to the finding.

Examples:

- Approved site photographs.
- Sanitised access logs.
- CCTV screenshots.
- Access-control reports.
- Inspection records.
- Maintenance documentation.
- Interview notes.
- Test records.

Avoid including:

- Unnecessary personal information.
- Unredacted employee details.
- Sensitive floor plans without a clear need.
- Access credentials.
- Security system configuration secrets.
- Unnecessary details about facility weaknesses.

## 8. Risk and business impact

Explain how the finding could affect the organisation.

Potential consequences include:

- Unauthorised facility access.
- Theft or damage.
- Exposure of sensitive information.
- Compromise of network infrastructure.
- Disruption to business operations.
- Loss of physical assets.
- Safety incidents.
- Regulatory or contractual consequences.

Distinguish confirmed impact from plausible scenarios.

## 9. Remediation recommendations

Recommendations should be practical and prioritised.

Examples:

| Finding type | Potential recommendation |
|---|---|
| Excessive access permissions | Conduct an access review and enforce least privilege |
| Unmanaged visitor access | Introduce formal visitor registration and escort requirements |
| Unaccounted keys | Implement a controlled key inventory |
| Inadequate CCTV coverage | Review camera placement and operational requirements |
| Poor alarm response | Establish notification and escalation procedures |
| Unrestricted server room access | Implement restricted access and periodic reviews |
| Inadequate contractor controls | Introduce time-limited access approval |
| Poor maintenance records | Establish documented inspection schedules |

## 10. Remediation prioritisation

A remediation roadmap may use:

- Immediate: Critical safety or security exposure.
- Short term: High-risk control weaknesses.
- Medium term: Significant procedural and technical improvements.
- Long term: Infrastructure changes and broader programme improvements.

Prioritisation should consider operational constraints and risk acceptance.

## 11. Retesting

Record:

- Original finding ID.
- Remediation implemented.
- Retest date.
- Retest method.
- Expected result.
- Observed result.
- Retest outcome.

Suggested outcomes:

- Remediated.
- Partially remediated.
- Not remediated.
- Risk accepted.
- Unable to retest.

## 12. Report handling

Physical security reports can contain highly sensitive information.

Apply appropriate controls:

- Restrict distribution.
- Encrypt reports and evidence.
- Use approved storage.
- Avoid public repositories.
- Redact sensitive details.
- Follow agreed retention and destruction requirements.
- Record report recipients.

Never publish sensitive facility vulnerabilities in a public repository.

## 13. Final quality review

Before delivering the report, confirm:

- Scope is accurate.
- Findings are supported by evidence.
- Severity ratings are justified.
- Recommendations are actionable.
- Personal information is minimised.
- Sensitive facility details are protected.
- Limitations are documented.
- Retest criteria are clear.
- The report has been reviewed by an appropriate assessor.
