# Cloud Forensics

## Overview

Cloud forensics examines evidence generated by cloud platforms, hosted services, identities, workloads and storage systems.

Cloud investigations often differ from traditional endpoint investigations because the underlying infrastructure may be managed by a provider.

Investigators must understand the available telemetry, shared responsibility boundaries and provider-specific retention policies.

## Common Evidence Sources

| Source | Potential evidence |
|---|---|
| Identity provider | Sign-ins, authentication methods, token activity |
| Cloud audit logs | API calls and administrative changes |
| Object storage | Object access, downloads and modifications |
| Virtual machines | Disk, memory and system logs |
| Network flow logs | Network communication metadata |
| Email platform | Message access and mailbox activity |
| SaaS audit logs | User and administrative activity |
| Container platform | Workload and orchestration events |
| Key management | Key access and configuration changes |

## Cloud Investigation Challenges

### Shared Responsibility

Cloud providers manage some layers of infrastructure, while customers remain responsible for others.

The exact boundary depends on the service model.

Investigators may not have direct access to:
- Physical storage
- Hypervisor memory
- Provider infrastructure logs
- Underlying network devices

### Evidence Retention

Cloud logs may have limited retention or require explicit configuration.

Identify:
- Default retention
- Configured retention
- Export destinations
- Archive policies
- Data residency
- Provider-specific limitations

### Distributed Infrastructure

Cloud services may operate across regions and availability zones.

Record the relevant region and resource identifiers.

### Time Synchronisation

Cloud audit events commonly use UTC timestamps, but source systems may use different representations.

Normalise timestamps carefully.

## Identity Forensics

Investigate:
- Successful and failed sign-ins
- Unusual IP addresses
- New devices
- MFA changes
- Password resets
- New authentication methods
- Privilege escalation
- Application consent
- Token-related activity

Correlate identity events with endpoint and SaaS activity.

## Cloud Audit Logs

Audit logs may record:
- API calls
- Resource creation
- Configuration changes
- Permission changes
- Administrative actions
- Data access
- Key management activity

Examples of common platforms:

- Microsoft Azure Activity Log
- Microsoft Entra audit and sign-in logs
- AWS CloudTrail
- Google Cloud Audit Logs

Preserve raw exports where possible.

Record:
- Query filters
- Time range
- Region
- Account or tenant
- Resource identifiers
- Export time
- Collection method

## Object Storage

Investigate:
- Object reads
- Object writes
- Deletions
- Public access changes
- Bucket policy changes
- Access-control changes
- Unusual download patterns

Do not assume a publicly accessible object was actually accessed.

Correlate exposure with access logs where available.

## Virtual Machine Forensics

Potential evidence:
- Disk snapshots
- Memory captures
- Instance metadata
- System logs
- EDR telemetry
- Network flow records
- Configuration changes

Before acquiring snapshots, consider:
- Application consistency
- Encryption
- Snapshot permissions
- Operational impact
- Retention
- Region
- Provider-specific behaviour

A cloud disk snapshot is not necessarily equivalent to a complete forensic image of a physical device.

## Container Forensics

Investigate:
- Container image provenance
- Image digests
- Container creation events
- Runtime process activity
- Container logs
- Orchestration audit events
- Secrets access
- Network activity
- Volume mounts

Relevant platforms include:
- Docker
- Kubernetes
- Managed container services

Containers may be ephemeral. Preserve relevant logs and runtime evidence before workloads are terminated.

## SaaS Investigations

Common evidence sources:
- User activity logs
- Administrative audit logs
- File-sharing events
- External sharing changes
- OAuth application grants
- Mailbox access
- API integrations
- Session records

Check whether logs are enabled and whether the subscription supports the required audit detail.

## Example: AWS CloudTrail Lookup

Using an authorised AWS CLI profile:

```bash
aws cloudtrail lookup-events \
  --start-time 2026-11-24T00:00:00Z \
  --end-time 2026-11-25T00:00:00Z
```

The command returns events available through the relevant CloudTrail lookup interface. It is not a substitute for preserving all configured CloudTrail log files.

## Example: Azure Activity Log

Using Azure CLI:

```bash
az monitor activity-log list \
  --start-time 2026-11-24T00:00:00Z \
  --end-time 2026-11-25T00:00:00Z \
  --output json
```

Access and retention depend on the subscription, permissions and configured diagnostic settings.

## Evidence Preservation

Recommended practices:
- Export audit records promptly.
- Preserve raw event data.
- Record filters and query parameters.
- Store exports securely.
- Hash exported files.
- Record tenant, account and region identifiers.
- Preserve relevant snapshots.
- Maintain chain of custody.
- Document provider limitations.

## Investigation Workflow

1. Establish cloud investigation authority.
2. Identify affected accounts and resources.
3. Determine relevant providers and regions.
4. Review logging configuration and retention.
5. Preserve audit and identity records.
6. Acquire workload evidence where appropriate.
7. Investigate access and configuration changes.
8. Examine data access and sharing activity.
9. Correlate cloud and endpoint events.
10. Document evidence gaps and provider limitations.
11. Report findings.

## Common Mistakes

- Assuming cloud audit logging is enabled by default.
- Ignoring retention periods.
- Failing to record region and tenant.
- Treating snapshots as complete forensic images.
- Overlooking SaaS audit logs.
- Ignoring identity and token activity.
- Assuming a public resource was accessed.
- Failing to preserve raw exports.
- Ignoring provider shared-responsibility boundaries.
